# 当前机器人参数与 Franka 真机接口审计

当前状态（2026-10-23）：READY 的 robot_facts.control_profile 明确列出位姿/关节目标、开口/抓取模式及参数，并列出未开放的独立速度、力矩/末端力、阻抗、homing、标定、碰撞阈值与部分力学反馈。同步提交与几何筛查是软件能力，软件速度/工作区限制不是完整硬件能力边界；没有声明真机驱动或力学模型已完成标定。以下正文保留为早期审计快照，不作为当前 Agent 的工具说明。


实施状态补充：下文是 grasp-v2 实现前的审计快照。随后共享多臂控制器已增加 `gripper.mode=grasp`、30..70 N 请求力、宽度容差及明确的驱动反馈，并将总开口速度上限改为 0.10 m/s。原位置模式保持，末端连续力控制仍未开放。行为语义以 [当前工具参考](../.agents/skills/robot-collaboration/references/tools.md) 为准；校验与 Oracle 物理记录在 `runs/beam-handoff-grasp-20261022/`。这不是已完成真机硬件标定的声明。

日期：2026-10-22。范围：当前 Panda/Franka Hand 任务动作、八臂木条场景、原 Menagerie MJCF 夹爪以及已有 Oracle 抬升记录。仅审计，未修改动作工具、Skill、Prompt、场景或执行器参数，未进行新的传递试验。

## 结论

1. 位姿、关节目标、运动速度、夹爪开口和开合速度具有真机控制对应物，但当前仿真控制器不等于已完成真机驱动适配。
2. Franka Hand 真机确有可请求的抓取力参数：官方 `Gripper::grasp` 的 force。当前项目缺少这一抓取模式，只实现原 MJCF 的位置开合。
3. 真机的目标抓取力、控制器输出力上限、碰撞检测阈值是三种含义。不能把 MuJoCo forcerange 或碰撞阈值改名为 force_n 后就声称实现了真机抓力控制。
4. 上轮约 2.25 N 是当前仿真抓取姿态下的腱驱动力，不是 Franka Hand 的额定夹持能力，也不能与手册的夹持力数值不经传动定义直接等同。

## 官方依据

- [Franka Hand 产品手册 220010/1.2/EN，第 10 页](https://download.franka.de/documents/220010_Product_Franka%20Hand_1.2_EN.pdf#page=10)：连续抓取力可调范围 30–70 N；行程 80 mm；每指速度 50 mm/s。这是所查手册版本的规格，不是任意夹爪或固件的通用范围。
- [libfranka Gripper](https://frankarobotics.github.io/libfranka/0.20.4/classfranka_1_1Gripper.html)：move 接受开口与速度；grasp 另外接受抓取力及两侧宽度容差。grasp 中 width 的语义是预期物体尺寸，不能照搬当前“关到零、碰到物体就停”的成功判定。
- [GripperState](https://frankarobotics.github.io/libfranka/0.20.4/structfranka_1_1GripperState.html)：标准状态包含开口、校准后最大开口、is_grasped、温度和时间，没有逐指接触对象身份或实测法向力字段。
- [FCI 概览](https://frankarobotics.github.io/docs/overview.html)：真实 Arm 提供关节位置/速度、笛卡尔位姿/速度、关节力矩等控制模式，由实时控制层执行。
- [控制接口要求](https://frankarobotics.github.io/docs/robot_specifications.html)：轨迹还受加速度、jerk 等要求约束；当前仿真的速度限制不能替代整套真机要求。不将其中 FR3 特定数值直接当作旧 Panda 的额定极限。
- [Robot 配置接口](https://frankarobotics.github.io/libfranka/0.20.4/classfranka_1_1Robot.html)：阻抗、TCP/坐标系、负载模型和碰撞检测行为有独立配置接口。负载模型改变的是补偿认知，不会改变真实物体质量；碰撞阈值改变的是触发条件，不是夹爪用力目标。
- [MuJoCo actuator 定义](https://mujoco.readthedocs.io/en/stable/XMLreference.html#actuator-general)：forcerange 对已计算的执行器力进行截断。

## 当前参数分类

| 当前字段／配置 | 真机对应与审计判断 | Agent 权限建议 |
| --- | --- | --- |
| move.target_m、delta_m、quaternion_wxyz | 可由真机笛卡尔运动接口与轨迹层实现；不是直接跳到目标姿态 | 保留为正常动作，控制层生成受限轨迹 |
| joint_rad、joint_speed_rad_s | 有关节运动对应；当前最高 0.9 rad/s 是本项目限制，不是 Panda 额定极限 | 允许在已配置范围内选择 |
| speed_m_s、angular_speed_rad_s | 是真实运动中有意义的速度选择；当前 TCP 0.005–0.15 m/s 等范围是软件设定 | 保留，硬件适配层检查真实机型约束 |
| gripper.width_m、state | 真机可设置开口；当前 0–0.08 m 与所查标准 Hand 的行程对应 | 保留，运行前以实际指尖与 homing 的 max_width 为准 |
| gripper.speed_m_s | 真机有开合速度；当前字段是总开口变化率，不能不经单位核对照搬驱动参数 | 保留并对齐速度定义、范围 |
| 当前开合参考最高 0.16 m/s | 对称两指意味着每指 80 mm/s，超过所查 Hand 手册的每指 50 mm/s 标称速度；实际仿真速度可能因负载更低，但参考上限仍未对齐 | 后续应修正范围，默认总开口 0.08 m/s 不存在这一数值超出 |
| 计划中的 force_n | 对应真实 grasp 的请求抓取力；目前工具不接受，也没有该控制模式 | 实现与验证后可开放，在具体硬件范围内选值 |
| epsilon_inner_m、epsilon_outer_m | 真机抓取宽度容差，影响成功判断，不是物理吸附、位姿纠正或力提升 | 未来 grasp 模式可提供合理范围／默认值 |
| forcerange、ctrlrange | 当前是仿真执行器输出／输入边界；不是上述真机 grasp.force 的等价物 | 固定为被标定的驱动配置，不作为提高额定能力的动作 |
| XML gainprm、biasprm | 仿真电机/位置伺服模型参数，不是公开 Hand 抓取命令参数 | 工程标定；Agent 不直接改 MJCF |
| 关节/笛卡尔阻抗 | 真机存在，但不等于任意修改仿真电机增益；当前未开放明确对应模式 | 需要时单独做有定义的控制接口，不用它替代抓取力 |
| 关节硬范围、额定速度/力矩、最大开口 | 设备能力与安装结构；软件可收紧，不能通过修改 XML 声称真机变强 | 保持在固定设备边界内 |
| setLoad 对应的负载质量/重心/惯量描述 | 真机有负载模型配置，必须描述实际载荷；与改变 MuJoCo body_mass 不同 | 明确属于模型配置，不能用错误标定减少真实重量 |
| 接触摩擦、木条质量/惯量/尺寸 | 是物体与表面属性；更换物体或材料是新场景条件，不是运行时机器人命令 | 冻结任务物理条件 |
| noslip_iterations、timestep、solver、solref/solimp | 数值仿真／接触模型设置，无普通真机动作命令对应 | 工程配置，不交给任务 Agent |
| stop | 可提供真实停止行为，但项目的受控减速保持不是硬件急停，亦不自动等价于真实 Gripper.stop 的抓持后果 | 驱动适配时明确状态与保持/释放含义 |
| check_motion | 机器人模型上的软件计算工具，有现实工程对应；不是硬件新增能力 | 可选计算，不承诺真实全场景无碰撞 |

当前握爪解析见 `robofrontier/robot_control.py` 的 validate/start/control；缺少 force 字段是代码事实。运动、速度和状态是合理抽象，但真机还需要实时轨迹执行与约束检查，不能直接运行当前 50 Hz MuJoCo 伺服循环到 FCI。

## 补充：真机存在但尚未向 Agent 开放的能力

| 能力 | 当前缺口与用途 |
| --- | --- |
| 抓取力与宽度容差 | 最直接的 Hand 接口缺口；应与开口 move 区分 |
| Gripper homing | 真机可校准当前手指的最大开口；当前场景直接使用配置初态，没有这一动作工具 |
| 直接关节速度／笛卡尔速度命令 | 当前只有位置目标加执行速度；不是独立、持续的速度控制模式 |
| 关节力矩／基于力矩的接触控制 | FCI 提供关节力矩接口，项目未开放。末端力控制需要控制器实现，不能凭新增 force 字段就成立，也与 Hand 抓取力不同 |
| 关节／笛卡尔阻抗 | 官方提供配置接口；当前未做对应、经过验证的 Agent 工具 |
| TCP 与 stiffness frame 配置 | 真机有对应变换配置；当前使用固定 TCP。属于工具/坐标标定，不会移动真实机械结构 |
| 负载模型配置 | 真机有 payload mass/COM/inertia 描述；当前无角色工具，且不能用它把物体实际减重 |
| 碰撞检测阈值 | 官方存在，但属于接触/碰撞检测配置，不是抓取强度或提高额定能力 |
| 关节力矩、外力/外力矩估计等反馈 | FCI 有对应数据；当前 observe 只给关节位置/速度、TCP 与夹爪位置等，未给这些力学反馈 |

是否开放与如何封装是另一个工程决定，不要求一次加入全部能力。Hand 标准状态不含每个接触点精确法向力，因此不能把 Oracle 的 MuJoCo 接触真值当成默认真机握爪传感器。

“真机没有”也要细分：NoSlip 迭代数、接触求解器参数等是数值仿真设置；物体质量、摩擦、惯量则是现实中存在的物理属性，只是不能通过机器人动作命令随意改写。IK 阻尼、步长、规划预算属于控制软件参数，现实软件也可使用，不是硬件新增能力。

## 提高 force limit 会不会变大

通用关系是：先由控制器计算输出，再受输出上限截断。仅当原输出已被上限截断、且控制器仍要求更大的输出时，放宽上限才可能增力。没有物体接触时，电机驱动力也不能等同为物体上受到的夹持力。

当前夹爪使用原位置伺服：在静态、闭合输入为零时，驱动力约为 −100 × 腱长度。在上轮约 22.49 mm 腱长度下得到约 −2.249 N。

更完整地，当前模型的未截断输出为 `F_raw = 0.01568627451*u - 100*L - 10*L_dot`。闭合时 u=0，静态 L_dot=0，L≈0.02249 m，因此 F_raw≈−2.249 N；再对这个结果作 forcerange 截断。该公式中的 L 是固定腱长度，两个手指的传动系数各为 0.5。腱驱动力与单指/双指接触力的数值不能混用。

摩擦不进入上述固定姿态下的执行器力计算。它影响的是接触处可承担的切向载荷，上界由接触法向力和摩擦系数共同决定。提高摩擦可能增加防滑承载能力，但不会把这个相同姿态下的 2.249 N 驱动力自动变成更大值。现实中换指垫与软件设抓取力也是两种不同操作。

在独立内存模型副本、同一姿态和控制输入下计算：

| 对称执行器力上限 | 输出腱驱动力绝对值 |
| --- | --- |
| 1 N | 1.000 N |
| 2 N | 2.000 N |
| 100 N（原模型） | 2.249 N |
| 200 N（反事实计算） | 2.249 N |

这里的 100/200 N 是检验 MuJoCo 截断语义的数值，不是给 Franka Hand 真机推荐的命令范围。原始场景没有被改写，未启动任何物理试验。可复现脚本为 `runs/beam-handoff-oracle-20261022/audit_force_limit.py`，结果在同目录 `force-limit-audit.json`。

因此，给当前代码增大 forcerange 不能解决这次弱抓持。真正增加请求抓取力需要抓取力控制模式；实际物体接触力还受机械传动、接触、驱动能力与控制误差影响。不能用 force_n 的指令值冒充测量值。

## 后续应对齐的最小接口

区分开口移动与抓取：前者选择开口、速度；后者选择预期物体宽度、速度、抓取力和宽度容差。采用官方 force 语义，避免把 force_limit_n 当作对 Franka 的直接映射。

默认可用所查 Hand 的范围建立待验证的配置，但必须固定具体夹爪、指尖、固件和单位约定。仿真底层可以实现受限的驱动／抓取控制，Agent 只发正常目标；标定过程检查请求力、仿真输出腱力和指尖接触响应之间的关系。支持抓取命令不代表每种抓取都成功，仍需抬升与交接检查。

反馈仅提供对应硬件真实可获得的状态；若没有实际力传感值，就明确标记 unavailable，不向 Agent 返回 MuJoCo 逐接触法向力冒充真机传感器。前两轮 Oracle 接触真值仍保留为工程诊断。

本次没有实现以上更改，也没有以修改后的力控制重跑成功。当前结论是接口与模型存在对齐缺口，而不是 Franka 真机被证明无法搬运 1.458 kg 木条。
