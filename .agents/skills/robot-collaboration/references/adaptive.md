# Optional bounded forks

Adaptive mode starts with one task Controller. `delegate` accepts a nonempty `scopes` list; each scope names `robots`, `goal`, `done_when`, and optional natural-language `constraints`. The Controller decides the split. Scopes in one batch use disjoint, currently owned, idle robots and inherit the same native parent history boundary. Disjoint ownership does not establish independent physical paths. Physics continues during setup. Native model and reasoning settings are explicitly pinned to the run settings. Creation cost is part of completion time.

Use the assigned connection and helper as for other tools. `delegate` returns after establishing the forks and delivering their assignments, not after their tasks finish. A pending response is unresolved setup: retry the original call ID. A known native ID is saved before history verification; recording it grants no action permission. Uncertain setup pauses dispatch for review, never automatically reforks or releases reserved robots. Setup has an infrastructure deadline; this is not a task execution limit. `work` shows outstanding delegations and current robot owners. Normal execution, image loading, action chunks and wait_events are unchanged.

A fork receives a current runtime assignment and its own connection. That assignment replaces inherited role identity, connection and finish authority; the frozen task, common evidence contract and Skill remain in force. Inherited pending parent calls and work are historical, not a queue to replay. Confirm current robot/scene evidence as needed. Operate only assigned robots, using explicit robot IDs. Delegates do not create further delegates or finish the team run.

The runtime assignment authorizes execution within its constraints; no separate business acceptance or per-step approval is required. Execute the bounded outcome autonomously. Use parent-directed messages for an enabling milestone, changed condition or exception; routine per-action approvals are unnecessary. The Controller may continue other work and handle whichever result arrives first. Delegates do not communicate directly with siblings.

Choose a finite outcome with a natural handback boundary. Before forking, jointly assess ready work, independent observation/decision effort, cross-scope coupling and the cost of handback. Include approach/withdrawal paths, payloads, neighboring results and shared commitments. Different robots or destination regions alone do not establish independence. Compare direct parallel commands, one delegate for coupled robots, and separate delegates for independent feedback loops. Judge a category or large scope by these dependencies; size and robot count are not evidence of benefit. This is a planning judgment, not a required tool call or separate approval.

Use the existing fields to make the boundary precise: goal names the finite result; done_when names verification and handback conditions for robots, payloads and shared access; constraints states relevant limits, commitments and changes needing coordination. Delegate local poses, order, speeds and views within that outcome. Prefer work with enough supported execution to repay delegation before its first unresolved prerequisite. Keep blocked downstream work in the Controller's frontier unless including it improves the split. Neither target count nor elapsed time sets a universal scope limit.

As progress changes, re-estimate remaining work and whether the split still enables useful concurrency. A verified access-release milestone may enable another scope before optional refinement ends. If waiting, repeated coordination or expanding recovery erodes the benefit, compare continued execution, a revised outcome/grouping and partial handback. Reassess an added repair or downstream job before expanding the assignment; the Controller retains overall planning and quality responsibility. A necessary local recovery can remain within scope. Agree material scope changes through the parent; preserve current commitments until changed and keep the work note current. No extra schema or per-action approval is required.

Normal execution ends at the assigned handback boundary with return_task followed by native turn end. Use existing tools for necessary action/message waits within that scope; a blocked step need not stop an independent prefix. When useful progress depends on substantial new coordination, report partial state and consider handback for reallocation. Choose waiting, pausing or returning by expected progress, holding/coordination cost and current commitments. Timed reviews can continue unfinished work; completed scopes are closed, and a later job uses a fresh fork with updated parent context.

Call `return_task` with `outcome` (`completed`, `failed` or `cancelled`) and `result` containing evidence references, current conditions and unresolved issues. Use completed only for the agreed done_when; describe partial progress and remaining work on failure or cancellation. Resolve physical calls, pending synchronization submissions and any still-unresolved signed group operation before returning; other independent scopes need not finish. The tool saves the full report in public/results, then releases robots and delivers a small status/result_ref notice; the Controller reads it as needed. A failed save retains ownership and sends no completion notice. Returning does not certify object goals. Any successful return_task closes this scope, including failed/cancelled outcomes: end the native turn without a waiting/yield loop. Closed scopes leave active monitoring and accept no new work. Native idle or a timer alone never releases ownership.

Include useful run-local lessons and their evidence/limits in the return report, or reference your own experience file. Controller selects what to adopt for further work. A fresh fork inherits the parent's history; point it to current adopted lessons or selected permitted references and mark superseded advice. This transfers experience without keeping a returned delegate active or installing a global Skill.

Controller can recover its own delegate status with work. To read a returned report on Claude, call work with {"delegate_id":"Delegate_..."}; the report is returned inline. In Codex, use the authorized result reference to read the public report file. Reports include the assigned scope and are Agent-produced evidence, not private evaluator state. Other roles read only results referenced to them through their permitted tools/messages.

A deliberate pause or wait retains this delegation and robot ownership; return_task closes it. Follow the communication reference's pause/confirmation rules. A delegate is temporary, not a standing per-robot Worker. If choosing to end a native reply while the scope is still needed, save the pending condition and a finite self-selected after_s; this optional recovery path is not a prerequisite to normal completion. The deadline can resume that active scope once when the session is idle and execution permits it. Returning control does not open the gripper or restore a home pose; report payload/robot conditions and remaining commitments.

An observed idle/error/attention native turn without return_task generates one delegate_stopped_without_return event per turn for Controller, including native ID, unresolved execution count and saved wait/deadline. Distinguish an explicitly saved review from an unexpected stop using those facts; the event alone is neither failure nor success and does not release control. An explicit waiting deadline or new Controller message can resume the existing scope; old mail and an inherited continuing state alone do not restart an unexpected stop. Controller can request missing handoff or a changed continuation and should check fresh state before changing commitments. Returned scopes stay closed. If cleanup cannot establish an action outcome, report it for engineering review rather than replay motion.

For a platform error with a freshly confirmed failed native turn, a new addressed Controller message can start a continuation only after physical calls are known settled. Saved timers and old work alone do not retry the error. If that continuation fails again, the existing request does not automatically retry it; inspect the new failure before choosing another request or engineering escalation. Message delivery is not permission to disregard an existing pause or replay motion.

Controller's work returns compact delegate_status with session timestamps, saved work metadata and active executions. work with delegate_id selects one own delegate's note/latest execution, including a returned delegate's result reference. A note is Agent evidence, not world truth. In a Codex host that exposes native read-only inspection, Controller may use read_thread/wait_threads on its own recorded delegate IDs for a question not resolved there; this does not authorize native creation, settings changes or messaging outside the task protocol. Prefer compact status for monitoring. Native read_thread can return long Agent messages despite output-truncation options: present selected fields/snippets rather than its entire result. Combine chosen RGB and robot feedback with these facts to investigate unexpected progress and the next parallel work. No complete session history is injected automatically.
