# Tool contract v0.24

In the CLI benchmark, call the bound `robot` tool with `op`, `data`, optional stable `call_id`, and `views` naming RGB images to return. For `observe`, select cameras in `data.cameras` and the images to load in `views`. The host binds your current role; after other local work call `robot` with `op:"inbox"` to check events. The Desktop helper examples below apply to Desktop, not the CLI host.

In Desktop or direct client use, use the repository's Python environment and assigned role connection:

```sh
"PYTHON" -m robofrontier.pipeline_client --connection "ROLE_CONNECTION" OP --data 'JSON'
```

Replace PYTHON and ROLE_CONNECTION with the values in the run's role file; quote paths. Run `--help` for syntax. `checkpoint` saves a work note, not a physical-world snapshot. A client chooses an ID before sending and stores the request locally. `--call-id ID` retries that same call; identical IDs with different parameters are rejected. `pending` lists unresolved local requests without submitting a robot action.

## Task tools

- `ready {}`: confirms role documents loaded, registers readiness and returns controlled_robots, run limits and robot_facts: compact static capabilities, TCP/status definitions, fixed base poses and per-robot TCP command bounds. Use these definitions when interpreting command/feedback positions and controller modes. All policy roles receive the same static robot facts. Bounds are admitted commands, not full-link envelopes or guaranteed safe zones. Current state comes from observe; detailed geometry through robot_model. No object state or task plan is supplied. It starts no physics actions.
- `observe {"cameras":["global"]}`: returns timestamped RGB paths and robot proprioception: TCP position/quaternion, joint positions/velocities, actual and commanded gripper width, gripper velocity and controller status. Camera names come from task metadata. Select and actually load images when needed; there is no automatic proof of viewing. No live object state/depth/contact truth is exposed.
- `move {"target_m":[x,y,z],"speed_m_s":number}` or `{"delta_m":[dx,dy,dz]}`: world-frame TCP position; optional `quaternion_wxyz:[w,x,y,z]` chooses world orientation and `angular_speed_rad_s` its rate. An orientation-only move holds the current TCP position. Omitted orientation retains the current reference. Quaternions are normalized; zero/nonfinite values fail. Robot-only IK validates position and orientation; a failed solve is not proof that every pose/seed is impossible. No object selection, grasp or collision-free path is inferred.

Pose interpolation uses the shorter quaternion rotation; a final orientation alone does not specify signed winding or a longer path. Choose finite intermediate poses when direction/path matters. Object motion follows contact, not the requested tool angle. Completed commands keep the current pose and established grasp across observations, waits and normal ownership handback; robot holding is not proof of the object's setting.
- `move {"joint_rad":[q1,q2,q3,q4,q5,q6,q7],"joint_speed_rad_s":number}`: optional joint-target mode. It is mutually exclusive with Cartesian/orientation parameters. Soft joint limits, endpoint TCP command bounds, reference velocity/acceleration and tracking limits still apply. Joint feedback arrays are available with full tool detail.
- `gripper {"width_m":0.05,"speed_m_s":0.04}`: choose an aperture within READY’s measured robot range and a total aperture reference rate. Alternatively use `state:"open"` / `"close"`, with optional speed. Width and state are mutually exclusive. The width uses the aperture-position drive declared by READY; force-held grasp is a separate operation. Feedback includes initial/target/measured width, measured-start direction, `target_width_reached`, and `grasp_verified:false`. Opening or holding must settle near the requested aperture: excessive opening and insufficient opening both fail tracking. Closing can settle above target without implying a grasp or verified contact; widening beyond its starting aperture is a tracking failure. Decide recovery from feedback and chosen RGB; no automatic physical retry occurs.
- `gripper {"mode":"grasp","width_m":0.045,"force_n":50,"speed_m_s":0.04}`: request a closing grasp at an expected object width, not a zero-aperture close. `force_n` is this Hand profile's total opposing finger drive setpoint (30..70 N; half per finger), not measured contact force. Optional `epsilon_inner_m` / `epsilon_outer_m` are positive width tolerances up to 0.01 m, default 0.005 each. A settled nonempty opening inside that interval returns `is_grasped:true`; a stalled jaw outside it or empty close fails. This is a width/settling inference and `grasp_verified:false` remains: lifting/retention still needs verification. The controller uses no object identity, pose or contact truth. `measured_grasp_force_n:null` means that sensor is unavailable, not zero force.

`mode:"move"` is optional for the original aperture operation. Total aperture speed is bounded at 0.10 m/s by this Hand profile. A completed grasp maintains force through later arm moves and after native/tool turn end until another gripper command. An opening move restores position control from measured aperture. Failed, timed-out or explicitly stopped unfinished grasp cancels force closing and holds measured opening without an automatic open/retry; holding that opening does not guarantee retaining a payload. Stopping an arm move preserves an already completed grasp. This is the project stop contract, not a claim that every native hardware stop has the same holding semantics.
- `stop {"call_id":"ACTIVE_ACTION_ID"}`: request bounded braking of the selected own action; it does not pause physics, release the fingers or undo motion. Acceptance is not stopped confirmation. Query/wait on the original action ID: a settled stop terminates it as `failed` with `reason:"stopped_by_agent"`; this is an intentional interruption, not a grasp assessment. A stale ID cannot stop a newer action.

For move, gripper and stop, a Worker controls its bound robot; Controller/delegates specify `robot:"A"` from controlled_robots. READY returns actual static `robot_facts.shared_capabilities`, action limits and available cameras; robot_model gives detailed geometry. Per-robot `tcp_command_bounds_world_m` in robot_facts is the authoritative command range in every scene. Select speeds within those limits. Stop and motion admission keep the same ownership in every topology. Continuous arm torque/wrench control, simulator reset and scene mutation are not policy tools. READY robot_facts.control_profile names the supported parameter subset and missing hardware modes; it is not a claim that every real-hardware capability is exposed. Software limits are not the full device envelope. Hand grasp-force selection is separate from arm force control. The simulated Hand uses a declared force/speed drive law within its original effort ceiling; it is not a complete hardware dynamics calibration.

READY's `execution_timing` defines a bounded action budget computed from requested travel/rate plus base time and margin. Accepted execution records include the estimated reference duration and actual timeout. This is a deadline, not a guarantee of reach, grasp or collision clearance. Requests exceeding the maximum budget fail before execution; choose speed or segmentation yourself. At timeout the executor stops advancing the target and brakes, retaining the original call until settled; a settled timeout returns failed. Failure to establish a settled stop returns uncertain and requires engineering review; it does not free the robot for another action or delegate. HTTP/client timeout is separate: query/retry the same ID rather than infer physical cancellation.

- `robot_model {}`: compact static robot-model summary, controller/check limits, model_id and result_ref to the full robot-only JSON. `robot_model {"robot":"A"}` returns that robot's detailed transforms, joint ranges, TCP and collision geometry with the same full-model reference. Select details or read referenced fields as needed; the file contains no current object state. No prior robot_model call is required for move or check_motion.
- `check_motion`: optional read-only comparison of candidate simultaneous moves. When uncertain full-arm overlap would cause waiting or cancellation, [motion screening](motion-check.md) gives the interface and coverage. Choose whether its information is worth the call; it is not a prerequisite for move and needs no preceding robot_model call.
- `send {"to":["Coordinator"],"text":"…","reply_to":"m1"}`: reply_to optional. Sending is nonblocking with respect to recipient decisions.
- `inbox {}`: obtains a bounded batch of pending messages and system events; remaining_messages reports mail still queued. `history {}` returns all your own sent/received business messages without pagination; use it when conversation recovery needs it.
- `work {}`: reads your saved note, continuation state/deadline, latest execution and active_executions keyed by own call ID. Controller may have multiple active robots. Coordinator's `team {}` returns Worker work timestamps/revisions, execution and session status. Notes can lag newer messages. Executor state proves neither business acceptance nor clearance; no object truth is exposed.
- `checkpoint {"state":"working","note":"pending work and commitments"}`: persists a note without yielding. It does not notify teammates of a business decision.
- `yield {"state":"waiting","note":"condition and next step","after_s":number}`: saves before you choose to end the native turn; the tool itself does not end it. States: waiting, available, continue. During an active run, waiting/available require your own finite after_s within run limits; there is no default period. Before START or while paused/ended it may be omitted. This is an optional turn boundary, not a phase required after each decision. Adaptive delegates normally finish via return_task; a deliberately saved wait retains their scope. Consider messages returned with yield before ending, and save material changes.
- `wait_events {"timeout_s":number,"call_ids":["ID"]}`: after START, wait for addressed mail, role system events, a listed own action becoming terminal, pause or run end. Choose a total deadline from 0 to the run's `max_check_interval_s`; default 30. `call_ids` is optional. The client reuses the original request across HTTP slices, without resetting the service deadline or making a new business decision. On `timeout`, choose whether to rewait, work, or save and end. `paused` means stop new work and save; `ended` means the run has closed. Native tool-host yielding still follows Codex's own behavior. Physics and other roles continue. Retry the same ID after uncertain transport; use a new ID for a new completed wait.
- `job {"call_id":"ID"}`: returns your own action status. accepted/running means not finished; completed/failed is the execution outcome; uncertain means execution cannot safely be inferred after disruption. Never treat a timeout as non-execution.
- `finish {"note":"completion evidence"}`: Coordinator, any peer Worker, or the single Controller proposes finish in its topology. Rejected while actions run or are uncertain. Verify the task's actual finish conditions; sustained holding and release are different outcomes. Private evaluation provides no corrective object coordinates to policy.

Adaptive mode additionally supports `delegate {"scopes":[{"robots":["A"],"goal":"chosen outcome","done_when":"chosen verification","constraints":"chosen limits"}]}` for Controller and `return_task {"outcome":"completed","result":"evidence and unresolved issues"}` for a delegate. return_task saves the report first; only status and result_ref are delivered to Controller. Read full reports on demand from the referenced file. Read [bounded forks](adaptive.md) for setup, identity and return semantics. `work` includes outstanding scopes and ownership; `wait_events` receives first-return events without waiting for all delegates. These operations are unavailable in the other experimental modes.

Adaptive Controller also receives compact delegate_status in work: native session IDs/status/timestamps, saved work metadata and active execution IDs. work {"delegate_id":"Delegate_…"} selects one own delegate's saved note/latest execution or returned result reference. It does not expose another role's inbox or private evaluator. A stopped native delegate that has not called return_task produces delegate_stopped_without_return through the same bounded system-event delivery; this is not a completed task or a control handback. See the adaptive reference for recovery and read-only native inspection.

Each `checkpoint` or `yield` replaces the saved review deadline: `after_s` sets it relative to that save; omission clears it. A saved deadline triggers at most one continuation for that saved revision, not periodic polling. While the run is active, the running administrative dispatcher can deliver a due continuation once the native session is idle and execution state allows it; it does not interrupt an active turn. Choose a new deadline when another review is needed. `wait_events` has its own request deadline and does not set this saved deadline.

Every response identifies the call. Both Coordinator and Worker tool returns attach bounded role inbox batches, including during an active native turn. Ordinary mail and system events share the batch budget; remaining_messages and remaining_events report further queued items. `delivery_id` and `system_events` are transport metadata, not new business message categories. The next client request acknowledges delivery only. New arrivals after that response remain queued; use inbox for another batch when needed. This is tool-boundary delivery, not cancellation or per-message steer.

For `move` or `gripper`, optional `"wait":false` returns after acceptance so you can communicate, observe or plan while your arm moves. `execution_status:running` is not completion. The action keeps its original call ID; use `job` or `wait_events` with that ID. One arm still accepts only one physical action at a time. Default `wait:true` returns at completion. Neither option interprets a plan or schedules future motions automatically.

These actions also accept `"cameras":["global","A_front"]` for the completion observation. Choose allowed names from READY/task metadata; generated scenes may also have top and board_top; `[]` returns robot feedback without rendering RGB. Omission preserves the selected robot's front/side defaults for direct clients. Nonblocking actions save the selected completion observation under the original call, retrievable with job; a query does not recapture it.

`run_ended:true` means the team run has closed. Late messages can still be saved for audit; they cannot reopen execution and do not trigger further team work. No new motion is accepted after finish.

`run_paused:true` means engineering paused the run. Stop new physical work and save waiting; it is not a grasp failure or permission to recreate the world.

## Desktop: one operation with selected images

The frozen `public/inputs/role_tools.js` helper can return one chosen operation's JSON and selected actual RGB images in the same outer tool call. No MCP server is required. Replace these path placeholders from the role file:

```javascript
const quote = s => "'" + s.replaceAll("'", "'\\''") + "'";
const source = await tools.exec_command({cmd:"cat "+quote("RUN_DIR/public/inputs/role_tools.js"),max_output_tokens:6000});
if (source.exit_code !== 0) throw new Error("Tool helper unavailable");
const call = eval(source.output + "\nrobotTool;");
await call({tools, python:"PYTHON", connection:"ROLE_CONNECTION",
  op:"observe", data:{cameras:["global"]}, views:["global"], text, image});
```

For move/gripper, the helper requests the named views as the completion cameras unless data.cameras is explicit. Thus views:["global"] requests and loads global, while views:[] requests robot feedback only. Explicit data.cameras can capture additional cameras without loading them; select views from that list. For observe, data.cameras selects capture and views selects loading. For job, selected images come from the original action's saved observation with its original timestamp. A running job normally has no terminal image. The helper makes no extra observe call and retains the action result if loading fails. It performs no perception, motion selection or session management.

The helper prints compact feedback by default: TCP, gripper width, controller status, maximum absolute joint velocity, timestamps, selected paths and all outcomes/mail remain visible; joint arrays stay in the full returned object. Choose detail:"full" when joint configuration matters, or inspect the returned data in the same invocation without another physical call. The direct Python client also returns full feedback. The helper already prints its result; print additional fields only when useful.

### Desktop: local tools also deliver role events

Robot API responses already include inbox batches. A bare native/local tool does not: while you analyze RGB or inspect a child chat, messages can arrive without a robot call. Use the same frozen helper's roleStep for such permitted non-robot work:

```javascript
const quote = s => "'" + s.replaceAll("'", "'\\''") + "'";
const source = await tools.exec_command({cmd:"cat "+quote("RUN_DIR/public/inputs/role_tools.js"),max_output_tokens:6000});
if (source.exit_code !== 0) throw new Error("Tool helper unavailable");
const {roleStep} = eval(source.output + "\n({roleStep});");
await roleStep({tools,python:"PYTHON",connection:"ROLE_CONNECTION",text,image,
  operation:async()=>{
    const result=await tools.exec_command({cmd:"YOUR_SELECTED_LOCAL_COMMAND",max_output_tokens:3000});
    text(result.output);return result;
  }});
```

The callback may contain chosen analysis, selected image loading, a process poll or permitted read-only native calls. Print selected output normally. After it returns or throws, roleStep refreshes your own inbox once and emits role_events only for mail, system events, remaining batches, pause/end or an error. It returns the original operation value and preserves its exception. A failed inbox refresh is reported separately and never reruns the selected operation. It does not interpret mail or execute follow-up actions. Already-decided local calls can share one step; choose a new boundary before a decision needing new evidence. For waiting on team progress use wait_events. robotTool/robotSequence already deliver role events and need no extra roleStep wrapper.

This Desktop helper is not a global Codex tool-result hook: bypassing it with bare local/native calls bypasses this delivery boundary. Keep roleStep around subsequent tool/process polls as well. CLI roles use the bound `robot` inbox operation instead. An active model doing no tool calls receives queued events at its next robot boundary, not by running-turn steer.

One model decision may issue an already-decided local sequence of existing calls within one outer invocation, choosing its length and checks. Preserve each action's ID/result; return control for failures, uncertain outcomes, pause/end, system events or an unresolved shared-resource condition. Return to the model if proceeding requires interpreting a new image; loading pixels inside a script does not interpret them. Do not cross a condition that still needs another Agent's decision. This does not create an automatic conditional action queue.

The same frozen source also exports `robotSequence`. Load it with `eval(source.output + "\n({robotTool,robotSequence});")`. Pass the same base arguments plus `steps:[{op:"move",data:{target_m:chosenXYZ,speed_m_s:chosenSpeed},callId:"your-stable-id"}, ...]` and final `views`. Each step must be move/gripper with a distinct explicit callId; Controller includes robot in each data. Intermediate views create a model boundary. The helper stops for the conditions above and returns sequence metadata plus every result; next_step is the number submitted, not permission to continue after an unresolved result. Inspect/resolve the stop before submitting an appropriate remainder under the original IDs. Parallel independent sequences can use Promise.all, including on one Controller connection. No task planner or new physical primitive is hidden in this helper.

The optional messageBoundary is "step" by default: mail stops the chunk after the current action. Choose "sequence" for an already-decided self-contained segment whose commitments remain valid until its end, such as an agreed clearing movement. It retains every message/result and postpones model review until the finite segment ends; it neither filters relevance nor accepts requests for you. Keep a step boundary where new team decisions or revocable shared conditions could change the next action. Pause/end, system events, failure, uncertainty and intermediate images still stop either mode.

## Infrastructure boundary

Meta binds sessions, starts the run under its selected startup protocol, imports real Codex status observations and drives plan/claim/dispatch-result operations. Policy agents do not use these administrative operations. Meta's notifications contain a wake ID and trigger reason, never task instructions.

Session running state, saved work state and robot action state are separate. Automatic work continuation is based only on explicit saved work and recorded execution facts. Unknown actions or repeated receipt/continuation failures stop automatic continuation for review. Physical-owner loss ends this run; there is no physical restart or implicit reset.

## Concurrent motion and handoff clearance

Different Workers can submit independent actions concurrently. IK checks the requested endpoint; it does not certify swept-volume clearance or coordinate collision-free multi-arm trajectories. Optional check_motion screens nominal sampled whole-arm geometry under explicit limitations; its result is not a clearance event or motion authorization. A returned terminal action result is already execution evidence; use job for a missing/uncertain result or another concrete need, not after every successful action by habit.

Object release, clearing shared space and returning home are distinct milestones. When full-arm and receiving-path clearance can be verified, a completed clearing waypoint may enable the receiver while unrelated return work continues. Returning all the way home is not inherently a prerequisite. Current moves return at completion and expose no certified mid-motion clearance event; never treat an estimated partial retreat or TCP separation alone as proof that another arm may enter shared space. If clearance cannot be established, retain the relevant exclusion and wait or choose another independent task.


## Finite same-cycle action batches

`action_batch {"actions":[{"robot":"A","op":"move","parameters":{"delta_m":[0.01,0,0],"speed_m_s":0.04}},{"robot":"B","op":"move","parameters":{"delta_m":[0.01,0,0],"speed_m_s":0.04}}],"wait":false,"cameras":[]}` submits currently decided commands over owned robots. Each robot occurs once. All commands validate/reserve before any starts, in one physics cycle. This does not synchronize arrival, control shared-payload internal loads, screen collisions or schedule future tasks. Optional check_motion retains its stated exclusions.

For different robot owners, each submits its own subset through the same operation with `"sync_group":{"id":"chosen-id","robots":["A","B"],"timeout_s":60}`. The ID and complete roster/timeout must match. Submit exactly the roster robots currently owned by you, once per owner. The timeout is Agent-chosen within READY's limit and starts at the first submission; later arrivals/retries never renew it. Pending members reserve only their own robots; physics/other work continue. All owners' submissions are revalidated when complete, then use the same executor as a one-owner batch. A missing member at the deadline, failed commit revalidation, withdrawal, pause or shutdown before startup cancels the unstarted group. A malformed or unauthorized join is rejected without cancelling another owner's accepted part. Relative deltas are resolved again from the actual commit snapshot. Closed/committed IDs cannot be reused; choose a fresh group after new coordination. Synchronization carries executor facts, not another role's commands/mail, and does not create business approval or permit a Coordinator/Meta to control robots.

Each submission has its own durable call ID and member action_ids. Retry that original ID after uncertain transport. `pending` means waiting for group members, not motion. wait:false returns promptly; job on your batch ID reports the current whole-group execution_status, your full member records, and compact execution facts for other group members. Call completion and physical outcome are distinct; failed/uncertain batches never become physical success merely because the RPC completed. Own terminal member_feedback remains available. wait:true returns at the group's terminal/unknown result. wait_events accepts your batch/member IDs and returns on own member completion, addressed group events or the chosen deadline; query the batch for whole-group progress. Chosen cameras capture terminal observations; intermediate views require observe.

One member failure requests controlled braking of remaining group arm moves, preserving established force grasps; unfinished gripper commands remain individually tracked. Unknown startup retains ownership and requires review, not rollback/replay. `stop {"call_id":"YOUR_BATCH_ID"}` withdraws an unstarted signed group or requests agreed group arm braking after startup. This neither opens grippers nor certifies payload retention. To cancel a running gripper command use its own member ID and the existing stop semantics. A terminal/stale batch cannot stop newer work. Pending members and an unresolved signed group operation must be resolved before control handback or reassignment; unrelated groups/scopes do not form a team-wide barrier. Team finish requires no pending/running/unknown execution.
